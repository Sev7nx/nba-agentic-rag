# NBA Agentic RAG 助手 · 设计文档

> 版本：V1（两周 MVP）
> 日期：2026-11-16
> 状态：待确认
> 用途：个人使用 + AI 应用开发岗位简历项目

---

## 1. 背景与目标

### 1.1 要解决的问题

看 NBA 的信息是分散的：

- 虎扑看新闻，但信息太杂，想找一条有用的要翻很久。
- 腾讯体育看比赛。
- B 站看集锦。
- 想问「库里哪场比赛最经典」这类问题，要自己开好几个网站、搜好几轮。

目标不是再做一个体育资讯站，而是做一个**站在这些来源之上的中文问答助手**：你问一句，它去这些地方找，把杂乱的新闻筛掉，给你一个答案，并附上能点开的新闻或视频链接。

### 1.2 为什么现在做

- 用户两周内要开始投递 AI 应用开发岗位的简历。
- 需要一个能演示、能讲清楚、能体现 Agentic RAG 能力的完整项目。
- 之后可以边面试边迭代，不要求第一版就把所有功能做完。

### 1.3 成功是什么样

第一版做完时，应该同时满足：

1. **能用**：自己日常问 NBA 问题，答案和链接确实有帮助。
2. **能演示**：有一个公网可以打开的 demo，或者至少有一个能录屏演示的本地版本。
3. **能讲**：有一个 GitHub 仓库、README、架构图，能在面试里讲清楚每一层为什么这么设计。
4. **有证据**：有一组评测问题和指标，能说明检索和回答的质量，而不是「我觉得挺好」。

## 2. 用户与使用场景

### 2.1 用户

单用户，就是项目作者本人。不做账号系统、不做多用户、不做权限。

### 2.2 主要场景

1. **新闻与转会**：「勇士最近有什么交易传闻？」（时效性以搜索结果为准）
2. **经典比赛与历史**：「库里哪场比赛最经典？」「2016 年总决赛第七场发生了什么？」
3. **集锦与视频**：「找几个约基奇本赛季的助攻集锦。」
4. **球员与球队背景**：「文班亚马这个赛季的表现怎么样？」「凯尔特人队史有几个冠军？」

说明：V1 不保证实时比分、赛程和精确统计数据的准确性；这类问题通过网页搜索尽力回答，并标注来源和时间。精确数据查询放到 V2。

### 2.3 不覆盖的场景

- 实时直播、实时比分推送。
- 社交、评论、发帖。
- 多用户、付费、运营后台。
- 完整的 NBA 统计数据仓库（数据查询是辅助，不是重点）。

## 3. 范围

### 3.1 MVP 目标

1. 中文聊天界面，支持多轮追问。
2. 问题理解：识别球员/球队、问题类型（新闻、视频、历史、对比）、时效性（最新还是经典）。
3. Agent 规划：根据问题选择 1-3 个工具，并说明为什么选。
4. 工具集：
   - 本地知识库检索（RAG）
   - 新闻搜索（虎扑、腾讯体育、NBA 官方等；搜索服务可插拔）
   - 视频搜索（B 站、YouTube；按可访问性降级）
   - 搜索服务已实测：Tavily 覆盖虎扑/B站/腾讯体育，MVP 直接用 Tavily，见 7.1
   - 网页正文提取（读排名靠前的结果，避免只靠搜索摘要）
5. 证据处理：去重、来源评分、重排，保留 5-8 条高质量证据。
6. 回答生成：中文答案 + 行内引用 `[1][2]` + 可点击来源卡片。
7. 自检与重试：检查引用覆盖、链接可达、问题是否被回答；不合格时最多重试一次。
8. 个性化：设置主队和喜欢的球员，影响检索和排序，但不做推送。
9. 评测：20 道题的评测集，记录检索命中率、引用覆盖、回答质量、延迟和成本。
10. API 层：FastAPI 提供 `/api/chat`、`/api/profile`、`/health`，自动生成 `/docs`。
11. 交付：GitHub 仓库、README、架构图、demo 录屏或公网链接。

### 3.2 非目标（这一版不做）

- 多用户和账号系统。
- 推送通知、订阅、邮件。
- 实时比分、直播流，以及赛程/精确统计数据的准确性保证（V1 只做尽力而为的搜索回答）。
- 完整的数据统计平台。
- 移动端 App。
- 模型微调。
- 多 Agent 编排（放到 V2）。

### 3.3 反目标（什么情况下算失败）

- 只是把搜索 API 的结果原样贴出来，没有 agent 决策。
- 答案没有引用，或者链接点不开。
- 为了显得「智能」而编造事实。
- 单次问答超过 10 秒，或成本超过 0.2 元。
- 只能在本机跑，面试时无法演示。
- 面试时讲不清为什么用 agent、为什么用 RAG、检索质量怎么保证。

## 4. 约束

- **语言**：只用 Python。
- **基础**：编程基础一般，主要靠 AI 辅助开发（vibe coding）。
- **周期**：两周内完成可写进简历的 MVP，之后边面试边迭代。
- **成本**：API 费用要低，目标单次问答 < 0.2 元。
- **网络**：主要在国内环境使用，优先选择可直接访问的模型和搜索服务。
- **部署**：希望有公网 demo；如果部署受限，至少要有可录屏的本地版本。
- **版权**：只展示标题、短摘要和原文链接，不转载全文。

## 5. 方案对比与选择

### 方案 A：单 Agent + 多工具（已选择）

一个 LLM agent 配 3-4 个工具：本地知识库检索、新闻搜索、视频搜索、网页正文提取。Agent 自己决定用哪些工具、要不要组合，证据重排后生成带引用的答案。

- 优点：两周能落地；链路清晰；能展示 query 拆解、工具选择、检索、重排、引用；面试容易讲。
- 缺点：单 agent 的决策深度有限，需要刻意设计才不像「搜索套壳」。
- 技术栈：Python + LangGraph + Chroma + Tavily + DeepSeek/Qwen + Streamlit。

### 方案 B：多 Agent 工作流

Planner 拆问题，新闻/视频/本地检索并行，Synthesizer 汇总，Critic 检查事实和引用，再输出。

- 优点：更「Agentic」，简历更亮眼，能讲多 agent 编排。
- 缺点：两周对新手偏紧；调试和成本更高；容易变成「为了多 agent 而多 agent」。
- 结论：放到 V2，作为从单 agent 演进到多 agent 的升级故事。

### 方案 C：本地 RAG 为主 + 搜索兜底

先抓取虎扑新闻、球员资料、经典比赛文章建向量库，回答先查本地，查不到再联网。

- 优点：RAG 流程完整，检索质量可控，成本低。
- 缺点：Agentic 成分弱；语料抓取和维护耗时；新闻时效性差。
- 结论：不作为主线，但保留「本地知识库」作为一个 RAG 工具。

### 最终选择

方案 A：单 agent + 多工具，保留本地向量库作为 RAG 工具。这样既有真正的 RAG 检索，又有 agent 的工具选择和多步决策；两周能落地，面试也能讲清楚。

## 6. 系统设计

### 6.1 总体架构

```
┌──────────────────────────────────────────────────┐
│ Streamlit UI                                     │
│ 聊天窗口 / 主队与球员设置 / 来源卡片 / 调试轨迹    │
└───────────────────────┬──────────────────────────┘
                        │ HTTP / SSE
┌───────────────────────▼──────────────────────────┐
│ FastAPI 后端（/api/chat、/api/profile、/docs）     │
└───────────────────────┬──────────────────────────┘
                        │
┌───────────────────────▼──────────────────────────┐
│ Agent Orchestrator（LangGraph）                   │
│                                                  │
│ analyze_query → plan → execute_tools             │
│       ↑                    │                     │
│       │                    ▼                     │
│  refine_query ←──── grade_evidence               │
│                            │                     │
│                            ▼                     │
│                       synthesize                 │
│                            │                     │
│                            ▼                     │
│                        verify ──失败──┐          │
│                            │          │          │
│                           END         └──→ 重试  │
└───────────────────────┬──────────────────────────┘
                        │
        ┌───────────────┼────────────────┬──────────────┐
        ▼               ▼                ▼              ▼
   local_rag      search_news      search_videos    fetch_page
   Chroma+BGE     Tavily(虎扑/腾讯)  Tavily(B站/YT)   Tavily extract
```

### 6.2 一次问答的完整流程

1. Streamlit 收集问题和设置，通过 FastAPI 的 `/api/chat` 发起请求。
2. `analyze_query`：用结构化输出识别实体、意图、时效性和语言。
3. `plan`：生成工具调用计划，最多 4 个工具调用，并给出选择理由。
4. `execute_tools`：并行执行工具，记录每个工具的耗时和结果数量。
5. `grade_evidence`：去重、按来源质量和相关性重排，保留 5-8 条证据。
6. `synthesize`：生成中文答案，带行内引用和来源卡片。
7. `verify`：检查引用覆盖、链接可达、问题是否被回答；不合格则 `refine_query` 后重试一次。
8. FastAPI 通过 SSE 把答案和调试轨迹流式返回给 Streamlit。

### 6.3 Agent 状态机

状态字段：

| 字段 | 说明 |
|---|---|
| `question` | 用户原始问题 |
| `chat_history` | 最近 N 轮对话 |
| `user_profile` | 主队、喜欢的球员 |
| `analysis` | 实体、意图、时效性 |
| `plan` | 工具调用列表及理由 |
| `tool_results` | 各工具返回的原始结果 |
| `evidence` | 去重、重排后的证据 |
| `answer` | 最终答案 |
| `citations` | 引用列表 |
| `rounds` | 当前检索轮次（最多 2） |
| `trace` | 每一步的耗时、token、成本 |

### 6.4 工具设计

| 工具 | 输入 | 输出 | 来源 |
|---|---|---|---|
| `local_rag` | 问题、实体、top_k | 本地知识库片段 + 元数据 | Chroma |
| `search_news` | 查询、时间范围 | 新闻标题、摘要、来源、链接、日期 | 搜索适配器，限定虎扑/腾讯/NBA 官方等 |
| `search_videos` | 查询 | 视频标题、站点、链接、缩略图 | 搜索适配器，限定 B 站/YouTube |
| `fetch_page` | URL | 正文纯文本 | 搜索适配器的正文提取能力 |

约束：

- 单次问答最多 4 个工具调用、2 轮检索。
- 新闻默认最近 30 天；历史问题不限时间。
- `fetch_page` 最多读 2 个页面，避免延迟和成本失控。

搜索层做成 `SearchProvider` 接口。D0 已实测：Tavily 用 `site:` 查询可以覆盖 bbs.hupu.com、bilibili.com、sports.qq.com（各返回 5 条有效结果），所以 MVP 主 provider 定为 Tavily；Serper/博查作为 V2 fallback。

注意：Tavily CLI 在 Windows 控制台打印中文 JSON 有编码 bug；应用内直接用 Python SDK/API，不经过 CLI。

### 6.5 本地知识库与检索

**首批语料（约 100 篇）：**

- 50 位现役/历史球星资料。
- 30 支球队资料。
- 20 篇经典比赛、规则、术语解释。

**来源：**

- Wikipedia（CC BY-SA，保留署名和链接）。只在构建语料时通过代理抓取，运行时不依赖 Wikipedia。
- NBA 官方历史页面。
- 百度百科/NBA 中文资料（保留来源链接，只存短摘要）。
- 虎扑文章（只存标题、短摘要和原文链接，不存全文）。

**处理：**

- 切块 500-800 token，重叠约 100 token。
- 元数据：来源、标题、URL、日期、实体类型、实体名。
- 向量库：Chroma。
- Embedding：开发阶段用 BGE-M3（本地、免费、中文好）；部署时如果内存不够，换成更小的 `bge-small-zh-v1.5` 或 API embedding。
- 重排：BGE-reranker-base，先取 20 条，重排后保留 5 条。
- 可选增强：BM25 + 向量混合检索（时间够再做）。

构建脚本在本地运行，产出的 Chroma 索引随项目发布；部署环境不需要访问维基百科。

### 6.6 引用与链接

- 答案中的每个关键事实后面跟 `[1]`、`[2]`。
- 答案下方展示来源卡片：标题、站点、日期、类型（新闻/视频/资料）、链接。
- 链接返回前做一次可达性检查（超时 3 秒）；死链降级或丢弃。
- 原则：**没有来源就不说**。找不到可靠来源时，明确告诉用户，并建议换一种问法。

### 6.7 个性化

- 设置项：主队（单选）、喜欢的球员（多选）。
- 存储：本地 `data/profile.json` 或 SQLite。
- 用法：
  - 提问里出现「我的主队」「我最喜欢的球员」时，替换成具体球队/球员。
  - 检索结果排序时，匹配主队/球员的内容加权。
  - 首页展示相关的最近新闻（不做推送）。
- UI 上用标签展示当前设置，可随时修改。

### 6.8 失败处理与防幻觉

| 情况 | 处理 |
|---|---|
| 没搜到结果 | 明确说没找到，建议换关键词；不编造 |
| 来源互相矛盾 | 同时列出，说明分歧 |
| 链接打不开 | 丢弃或标注「链接可能失效」 |
| 自检不通过 | 改写查询重试一次；仍不通过则带保留意见返回 |
| 工具超时 | 用已完成的结果回答，并注明哪部分缺失 |
| 问题超出范围 | 直接说明只能回答 NBA 相关问题 |

## 7. 技术选型

| 层 | 选择 | 理由 | 备选 |
|---|---|---|---|
| LLM | DeepSeek-V3 / Qwen-Plus | 便宜、中文好、支持工具调用 | OpenAI / Claude（通过适配层切换） |
| Agent 编排 | LangGraph | 状态机清晰、可调试、简历友好 | 自己写 agent loop |
| 向量库 | Chroma | 本地、简单、够用 | FAISS / pgvector |
| Embedding | BGE-M3（开发）/ bge-small-zh（部署） | 中文效果好、免费 | API embedding |
| 重排 | BGE-reranker-base | 免费、效果明显 | Cohere Rerank |
| 搜索 | Tavily（已实测覆盖虎扑/B站/腾讯体育） | 中文源覆盖已验证，成本低 | Serper / 博查（V2 fallback） |
| UI | Streamlit | 纯 Python、开发快、1-2 天能跑 | Gradio |
| API | FastAPI + Pydantic | 自动 OpenAPI 文档、类型校验、简历加分 | Flask |
| 流式输出 | FastAPI SSE + Streamlit `st.write_stream` | 逐字显示，体感快 | 非流式 |
| 限流 | slowapi（FastAPI 中间件） | 保护公网 demo | 应用内计数 |
| 评测 | RAGAS + 自定义引用检查 | 指标成熟、能写进 README | 纯 LLM-as-judge |
| 观测 | JSONL trace + 可选 Langfuse | 先简单，时间够再上平台 | LangSmith |
| 部署 | Docker + Hugging Face Spaces / 魔搭创空间 | 可复现、国内可访问 | Render / Railway |
| 配置 | pydantic-settings + `.env` | 密钥不落代码 | — |
| 测试 | pytest + FastAPI TestClient + mock 外部 API | 覆盖 API 和核心逻辑 | — |
| 容器 | Dockerfile | 可复现部署 | 本地 venv |

### 成本与延迟目标

- 单次问答成本 < 0.2 元。
- P95 延迟 < 10 秒；用流式输出降低体感等待。
- 控制手段：缓存搜索结果和答案、并行工具调用、限制轮次、用便宜模型做分类和评测。

## 8. 两周 MVP 里程碑

### 第 1 周：把核心链路跑通

| 天 | 任务 | 完成标准 |
|---|---|---|
| D1-2 | 项目骨架、环境、密钥管理、FastAPI 骨架（/api/chat、/api/profile）、Streamlit 聊天页、一个搜索工具 | 页面能通过 API 提问并看到带链接的回答 |
| D3-4 | 新闻搜索、视频搜索、问题分析、计划展示、来源卡片、SSE 流式输出 | 三类问题都能返回可用结果 |
| D5-6 | 本地语料（30 篇）、Chroma、embedding、重排 | 本地 RAG 工具可用 |
| D7 | Agent 路由、证据重排、自检、失败重试 | 答案有引用，失败有兜底 |

### 第 2 周：让它像作品，而不是 demo

| 天 | 任务 | 完成标准 |
|---|---|---|
| D8-9 | 主队/球员设置、trace 面板、Streamlit UI 打磨、API 异常处理、缓存、链接检查 | 主队/球员生效，页面可展示 |
| D10-11 | 评测集、RAGAS、延迟和成本记录 | 有一张评测结果表 |
| D12-13 | README、架构图、演示录屏、部署（魔搭或本地录屏） | 公网可打开或录屏可演示 |
| D14 | 缓冲、面试问答准备 | 能讲清 10 个高频问题 |

### 如果时间不够，按这个顺序砍

1. 个性化设置（最后做）。
2. trace 面板缩成「显示原始 JSON」。
3. 视频搜索（先用新闻搜索兜底）。
4. UI 美化（动画、多页面、深色模式）。

FastAPI 层只保留必要接口：`/api/chat`（SSE）、`/api/profile`、`/health`。不要为了「API 完整」加一堆用不到的端点。Streamlit 的 UI 定制能力有限，不要在界面上花太多时间；优先核心链路、引用和评测。

**不要砍**：核心问答链路、引用、评测、README、部署/录屏。这四样是简历项目的骨架。

## 9. 评估方案

### 9.1 评测集

20 道题，覆盖 5 类：

- 新闻/转会（5）
- 经典比赛/历史（5）
- 球员/球队对比（4）
- 集锦/视频（3）
- 规则/术语（3）

每题记录：问题、期望关键事实、期望来源类型、是否必须有链接。

### 9.2 指标

| 指标 | 说明 | 目标 |
|---|---|---|
| 检索命中率 | 期望来源是否出现在证据里 | ≥ 70% |
| 引用覆盖率 | 关键事实是否都有引用 | ≥ 90% |
| 回答相关性 | 是否回答了问题（LLM 或人工评分） | ≥ 80% |
| 忠实度 | 答案是否忠于证据（RAGAS faithfulness） | ≥ 0.8 |
| 链接有效率 | 来源链接可打开比例 | ≥ 95% |
| P95 延迟 | 单次问答端到端时间 | < 10 秒 |
| 单次成本 | LLM + 搜索平均成本 | < 0.2 元 |

### 9.3 评估方式

- 自动：RAGAS（用 DeepSeek 做 judge，控制成本）+ 自定义引用/链接检查。
- 人工：抽 10 条答案逐条看，记录问题类型和失败原因。
- 结果写进 README，作为项目质量证据。

## 12. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 搜索服务额度不够或临时不可用 | 核心工具不可用 | 已实测中文覆盖；加缓存和 fallback 适配器；关注每日额度 |
| B 站/YouTube 链接地区受限 | 视频打不开 | 链接检查 + 同时给新闻/文字来源 |
| Agent 编造事实 | 答案不可信 | 引用 + 自检 + 无来源不回答 |
| 两周做不完 | 简历没东西可写 | 按优先级砍功能，保核心链路和评测 |
| FastAPI + Streamlit 两个服务联调/部署更复杂 | 拖慢进度 | API 只保留 3 个端点；本地用 docker-compose；公网部署时间不够就只录屏 |
| Streamlit UI 定制能力有限 | 界面不够产品化 | 用原生组件 + 自定义 CSS；把精力放在 Agentic RAG 和评测上 |
| 部署内存不够 | 公网 demo 起不来 | 换小 embedding 模型或 API embedding |
| API 费用失控 | 不敢演示 | 缓存、限流、便宜模型、限制轮次 |
| 版权问题 | 不能公开演示 | 只展示标题/短摘要/链接，不转载全文 |
| 新手调试困难 | 卡住 | 小步提交、trace、pytest、先跑通再优化 |
